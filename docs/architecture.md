# 架构与扩展边界

## 当前数据通路

```mermaid
flowchart LR
    repo[本地 Python 仓库] --> ast[analyzer / AST 静态分析]
    ast --> graph[models / 版本化 Graph]
    graph --> json[JSON 导出]
    graph --> mermaid[Mermaid 导出]
    graph --> api[server / 只读本地 API]
```

`models.py` 是各层的共享契约，避免图形界面绑定 AST 内部对象。分析器负责产生节点、边及可追溯的文件行号；导出器负责选择视图和入口可达子图；CLI 与 HTTP 层只负责输入输出。

## 下一阶段建议的模块

这些模块尚未创建，不包含空壳实现：

- `viewer/`：使用 `/api/graph` 显示模块图、入口调用图及证据详情；与解析器解耦。
- `source_reader.py`：只允许读取当前仓库内的源码范围，为节点详情提供上下文。
- `entrypoints.py`：识别 `__main__`、CLI 注册或框架入口，返回候选入口与理由。
- `tracing/`：在独立进程中执行用户指定场景。限制运行时间并记录调用事件；未来处理线程、协程挂起与恢复。运行超时不是隔离沙箱。
- `summaries.py`：可选大模型总结，要求每段模块职责关联源码证据。

## 图的语义

- `imports`：模块依赖候选边。
- `calls`：AST 能解析到仓库内符号的调用候选边。
- 未来的运行观察边使用独立 evidence 类型，且关联场景 ID，不能覆盖静态图。
- 调用图、执行时间线和变量数据流分别建模，不能用一条“调用”边代表三种关系。

第一版暂不承诺完整程序分析。优先验证“新人能否找到入口并理解关键模块”，再扩展语言和框架。
